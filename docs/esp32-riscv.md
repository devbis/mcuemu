# ESP32-C6 / ESP32-H2 (RISC-V): status and plan

Not a chip model yet. What exists is the groundwork: register headers and the
RISC-V part of the Unicorn fork. Both chips are RV32IMAC (the C6 also has a
separate LP core) with an IEEE 802.15.4 MAC.

## Register headers

`emulator/include/esp32emu/esp32c6_regs.hpp` and `esp32h2_regs.hpp` are
generated by `scripts/gen-esp-regs.py` from the SVD files of
[esp-rs/esp-pacs](https://github.com/esp-rs/esp-pacs) (`esp32c6/svd`,
`esp32h2/svd`):

```sh
scripts/gen-esp-regs.py --svd esp32c6.base.svd --chip esp32c6 \
    --out emulator/include/esp32emu/esp32c6_regs.hpp
```

Each peripheral gets `base`, `reg::`, `reset::`, `field::*_shift/_width` and
`irq::` (interrupt source numbers). The SVD describes layout only; behaviour
(self-clearing bits, timing, what an operation does) has to come from the TRM
and from driver code (`esp-hal`, ESP-IDF). Facts that matter:

- Base addresses differ between the chips (the H2 SYSTIMER is at 0x6000B000, the
  C6 one at 0x6000A000), hence one header per chip.
- The base SVDs are unpatched. The only unresolved template names in the
  peripherals we emit are `TIMG0`'s `T%sCONFIG` and friends; the generator reads
  them as timer 0, which is what esp-pacs' `_timg.yml` patch does.
- `derivedFrom` peripherals (UART1, TIMG1) reuse the base layout at their own
  address and interrupt.

## RISC-V in the Unicorn fork

`UNICORN_ARCH` now includes `riscv`. Stock Unicorn does not run a bare-metal
RISC-V chip: `ecall` and every other trap stopped the engine with
`UC_ERR_EXCEPTION`, and the host could not raise an interrupt (writes to `mip`
read back as 0, and `mie` only has the standard bits 3/7/11, while the ESP32
numbers its CPU interrupts 1..31). Our additions, in the same spirit as the
Cortex-M ones:

- `uc->guest_exception` for RISC-V: ecall, illegal instruction, address
  misalignment and access faults go to the guest's `mtvec`. `ebreak` and the
  end-of-run marker still stop the engine (`ebreak` as `UC_ERR_INSN_INVALID`).
- `uc_riscv_irq(uc, cause)`: the interrupt controller lives in the host (INTMTX /
  INTPRI and priority/threshold logic), which picks the winner and calls this
  with its number. It is taken with `mcause = 1<<31 | cause` through `mtvec`
  (direct or vectored) when `mstatus.MIE` allows, and stays asserted until
  `uc_riscv_irq(uc, -1)` (level behaviour; the ISR clears the peripheral and the
  host re-evaluates). It ignores `mie`/`mip` on purpose.
- A WFI that reaches the engine halts it with `pc` already after the `wfi`;
  restarting without a pending interrupt returns at once. The wrapper should
  decode WFI itself (as `cortexm::Core` does) rather than rely on that.

`tests/riscv/` (`riscvemu-tests`) covers these with small programs
(`tests/riscv/programs/*.s`, regenerated with `build.py` using an LLVM that has
the RISC-V target: `LLVM_BIN=/opt/homebrew/opt/llvm/bin python3 .../build.py`).

## `riscv::Core` (`emulator/src/riscv/`, library `riscvcore`)

The generic hart, in the role of `cortexm::Core`: memory map (host-backed
regions and `Bus` windows), a cycle clock (one cycle per instruction, inferred),
`run(until_cycle)`, the chip's service callback, instruction limit and reset
request. Chip facts stay out of it. Specifics:

- The CPU model is the SiFive E31 (RV32IMAC, M and U modes, no FPU), the closest
  stock model to the ESP32-C6 HP core and the ESP32-H2; the default model also
  has F and D, which those chips do not.
- WFI and ebreak are decoded in the code hook from the host copy of the code and
  never reach the engine. WFI sleeps the clock up to the next service deadline
  (idle chips cost nothing); any `set_interrupt()` wakes it, whatever
  `mstatus.MIE` says, as the spec allows.
- `set_interrupt(cause)` is level-sensitive: the controller drops it (usually in
  the register write that acknowledges the peripheral) with `set_interrupt(-1)`,
  otherwise the interrupt fires again after `mret`.
- The interrupt is taken at the next translation block boundary, so a few
  instructions can run after the store that raised it.

## ESP32-C6 chip model (`emulator/src/esp32/`, library `esp32emu`)

`mcuemu run --model ESP32C6 --firmware flash.bin [--for 1s] [--steps N]
[--trace-mmio] [--last-pcs]` runs a flash image from offset 0 the way the ROM
loader starts it. The model is incomplete: it is built by running real firmware
and implementing what the trace shows it needs, so each block states what is
documented and what is inferred.

What exists:

- **Boot**: the ROM loader is replaced by `Esp32::reset()`: it reads the image
  header (magic 0xE9) at flash offset 0, copies the RAM segments and jumps to the
  entry. The flash itself is the 4 MiB array behind SPI1/SPI0.
- **ROM** (`rom.cpp`): no ROM image; its region is filled with `ebreak` and the
  chip runs host code for the entries firmware calls (memcpy/memset/memmove/
  memcmp, libgcc 64-bit arithmetic, `ets_printf`, UART output, delays, cache
  functions as no-ops, software reset). Names and addresses come from
  `esp32c6_rom.hpp`, generated by `scripts/gen-esp-rom-symbols.py` from the ROM
  linker scripts of esp-rom-sys. An entry nobody handles is logged by name and
  returns 0. The ROM also leaves data in the top of the SRAM
  (`rom_spiflash_legacy_data`), which `reset()` recreates.
- **Cache MMU** (`SpiMem0`): the 256-entry table behind 0x42000000 with 64 KiB
  pages; writing an entry copies the flash page into the window.
- **Flash controller** (`SpiMem1`): the user-command path (RDID, RDSR, WREN, ...),
  commands complete instantly.
- **Interrupts** (`intc.cpp`): INTMTX (0x60010000) routes sources to the hart's CPU
  lines, PLIC_MX (0x20001000) enables, types, prioritises and thresholds them, and
  the winner goes to `riscv::Core::set_interrupt` (mcause = line number). The ROM's
  `esprv_intc_*` and `intr_matrix_set` are stand-ins over the same registers.
- **Timers**: SYSTIMER counters (16 MHz, latched reads) and comparators with their
  interrupts (the Zephyr kernel tick), LP_TIMER main counter (136 kHz), TIMG RTC
  calibration, a microsecond counter the PHY blob times its loops with. TIMG
  watchdogs and general-purpose timers: not yet.
- **UART0**: transmit FIFO only. `StatusBlock` serves registers that are only
  written and polled (the modem analog I2C master's calibration-done bit, ...).
- **PHY**: the RF front end is not modelled. `phy_get_romfuncs` returns a table
  whose entries are numbered ROM slots (`phy_romfunc[k]`); slots 20/21/23/24 are
  the analog I2C read/write/masked ops (storage with one "calibration done" bit
  forced), and a few digital PHY registers have forced "done" bits. That is
  enough for the first calibrations, not for the whole of `libphy`.
- **CPU**: Espressif's performance counter CSRs 0x7e0..0x7e2 (host-served through
  `uc_riscv_csr_handler`) and a PMP workaround in the fork (QEMU judged a fetch by
  the whole page, so a PMP region ending inside a page faulted).

Anything else in the peripheral window reads back what was written and is logged
with `--trace-mmio` (capped by `--trace-limit`, default 200000 lines: a polling
loop writes gigabytes).

### Debugging aids of `mcuemu run --model ESP32C6`

`--elf FILE` names addresses from the build's ELF; `--stub NAME|0xADDR[=VALUE]`
makes a firmware function return at once; `--no-phy-stubs`, `--trace-calls TIME` (every named function entry with sp after TIME, a histogram of hot code
and the lowest sp), `--break`, `--log-at` (registers and
the stack at an address, then go on), `--watch`, `--dump ADDR[:LEN]`, `--trace-irq`,
`--trace-rom`, `--last-pcs` (the last instructions, named with `--elf`), the CSR/PMP
state and, when the firmware's own fatal handler prints through the UART, its
message. A breakpoint on the trap vector stops only on exceptions, not interrupts.

### IEEE 802.15.4 MAC and the shared air (`ieee802154.cpp`)

The MAC (0x600A3000 on both chips; the esp-pacs SVD gives the H2 0x60047000, which
ESP-IDF's `reg_base.h` contradicts) is written from the open drivers (esp-hal's
esp-radio `ieee802154/{raw,hal,pib}.rs`, ESP-IDF `esp_ieee802154_dev.c`): COMMAND
opcodes (TX, RX, CCA+TX, ED, STOP, timers 0/1), DMA of the frame (`{PHR, MAC bytes}` out,
`{PHR, MAC bytes, RSSI, LQI}` in, PHR counting the FCS the hardware adds and checks),
EVENT_STATUS/EVENT_EN with write-one-to-clear, the abort reasons and their enables,
the address filter (promiscuous, or PAN/short/extended address against the enabled
interfaces INF0..3), hardware ACKs (an ACK 192 us after a unicast frame that asks for
one, the pending bit from `ACK_FRAME_PENDING_EN`, and RX-ACK matching by sequence number
when `HW_AUTO_ACK_RX_EN` is on) and timer0/1 in microseconds. It joins a
`mcuemu::VirtualAir` through `Esp32::connect_radio`, so frames cross to and from the
nRF52840, EFR32MG21 and TLSR8258 models. Inferred rather than documented: the TX/ACK
turnaround times, the interface-enable bit position (esp-hal writes its mask at bit 29,
the SVD says 28: both enable), a repeated RxStart while listening being a no-op, and
ACK frames reaching software when `HW_AUTO_ACK_RX_EN` is off (zigbee-rs relies on it).
Not modelled: enhanced ACKs, security, coexistence, ED results from the air.

### GPIO and UART0 (`gpio.cpp`, `esp32.cpp`)

GPIO/IO_MUX model pads used as plain GPIO: OUT/ENABLE with W1TS/W1TC aliases, IN (the level the board gives the pad,
high until told otherwise), per-pin interrupt type/enable with a latched status, and `FUNCn_OUT_SEL_CFG` = 0x80 for
a pad that follows OUT; IO_MUX pull-ups/downs decide the pull the board sees. Peripheral signals through the GPIO
matrix are not modelled. In `sim` the pads are `GPIO0`.. nets (`examples/devices/esp32h2_devkit.yaml`: LED on GPIO8,
BOOT button on GPIO9, read off the zigbee-rs image). UART0 has a receive FIFO (128 bytes) with RXFIFO_FULL/TOUT
interrupts and the transmit ones; no baud-rate timing.

### ESP32-H2 (`--model ESP32H2`, `esp32h2` in `sim`)

`esp32emu::Layout` holds what differs between the chips (sizes, 96 MHz CPU and 32 MHz
XTAL, peripheral bases, interrupt-matrix sources, the ROM symbol table). The whole
zigbee-rs `esp32h2-sensor.bin` flash image runs: the real ESP-IDF second stage
bootloader (ROM stand-ins for MD5, SHA-256, CRC32 and the flash read/write/erase
routines, which implement NOR semantics and refresh the cache window), then the esp-hal
application. What it needed beyond the C6 model: the PCR `BUS_CLK_UPDATE` strobe, the
PMA/trigger CSRs as storage (a widened host CSR range; the fork lets the host decline a
number), the regi2c master's two host control words, forced "done" bits in the PHY
digital window (0x814 state, 0x4a0), a hardware AES block (ECB, known-answer tested), a
factory MAC in the eFuse, GPIO (idle inputs read high), `mstatus.MIE` set at entry (esp-hal
only saves and restores it) and the PLIC threshold meaning "priority >= threshold".
`mcuemu sim examples/esp32h2_zigbee.yaml` joins the TLSR8258 sampleGW network, completes
the trust-center link key exchange and commits (`firmware_esp32h2_zigbee_join`). After a
software reset the model restarts the image (`--restart` in `run`); a chip reset also
restarts the SYSTIMER counters and clears registers no block models.

### State of the Zephyr 802.15.4 images

Both the local `esp32c6_devkitc` Zephyr build (`ESP_SIMPLE_BOOT`, flash offset 0)
and the released `esp32c6-end-device.bin` behave the same:

- Boot, MMU, kernel start, timer interrupts, threads and the Zephyr banner work.
- `register_chipv7_phy` (the PHY blob's init) cannot run: with only the forced bits
  above the calibration walks a call chain deeper than the main thread's 896-byte
  stack, which overruns the idle thread's initial frame, and a tick interrupt
  corrupts the interrupt stack. The model stands in for it by stubbing the PHY
  functions `register_chipv7_phy` and `phy_track_pll_internal`, found in the flash
  image by their first instructions when the cache MMU maps the page (`Config::stub_phy`,
  on by default; `--stub` still stubs any function by name or address). The blob is the
  same in every build, so this works on the released image without its ELF.
- Why it needs the stubs (investigated with `--no-phy-stubs`, `--trace-calls TIME` and `--elf`): the call chain
  `bg_thread_main -> z_sys_init_run_level -> esp32_init -> ... -> register_chipv7_phy -> bb_init ->
  chip_v7_set_chan -> ... -> wifi_get_tx_tab -> ram_set_chan_cal_interp` reaches 0x80 bytes below the 896-byte
  `z_main_stack` (frames of `txdc_cal_pwdet` alone fill it exactly), into the top of the idle thread's
  stack, where Zephyr keeps that thread's initial exception frame (and its TLS). The first run of the
  idle thread then `mret`s to a stack address and faults. This is the firmware's own call depth, so real
  hardware should overrun the same way; why it survives there is not understood (a different path through
  `libphy` with real eFuse calibration data, which the model leaves blank, is the open guess). Two model
  fixes shortened the init without removing the overflow: `wait_i2c_sdm_stable` finds the value it polls
  for (block 0x63, register 0 reads 0x5b) instead of timing out after 10 ms, and `get_tone_sar_dout` returns a
  rising ramp so the DC-offset scans stop after a few steps instead of 50 per phase (23 ms of
  virtual time down to about 5 ms).
- The image's Zigbee stack scans channel 11 only (its channel mask), sending beacon
  requests; the sampleGW coordinator forms its network on channel 15, so it does not
  join that network (a coordinator on channel 11 would, untested).

## Next steps

1. A PHY that needs no stubs on the C6 (the H2 blob runs with forced bits only): find out why the stack overrun
   is harmless on hardware (eFuse calibration data is the first thing to try).
2. The C6 Zephyr image against a coordinator on its channel.
3. TIMG watchdogs, the C6's eFuse (the chip revision reads as v0.0; `o_code calibration
   fail` is logged) and the H2's real temperature sensor (the model returns what the
   app writes to the analog registers).
4. Speed: the H2 sensor runs about 3.4x faster than real time while idle.
