# nRF52840 (Cortex-M4F)

The first Cortex-M chip in mcuemu: a Nordic nRF52840 on the Unicorn fork's ARM
backend. The model runs the CPU, the interrupt controller, the common
peripherals and the RADIO in IEEE 802.15.4 mode (BLE is not modelled, see
[Status](#status)).

```sh
./build/mcuemu run --model NRF52840 --firmware firmware/nrf52840-sensor.bin --for 5s
./build/mcuemu sim examples/nrf52840_promicro.yaml --for 10s
```

`mcuemu run` takes `--firmware IMAGE` (a raw binary placed at flash address 0),
`--for DURATION` (virtual time, default 1 s), `--steps N` (instruction limit) and
`--trace-mmio` (every peripheral register access on stderr, with the PC). In a
system file use `model: nrf52840`; pads are named like the datasheet
(`P0.00`..`P0.31`, `P1.00`..`P1.15`). `supply_mv` is the voltage the SAADC's VDD
input sees. The model has no variants and a fixed 64 MHz clock.

## Layers

- `emulator/src/cortexm/` (`cortexm::Core`) is generic Cortex-M3/M4 glue and has
  no chip knowledge: memory map, the 0xE000E000 System Control Space, SysTick,
  the DWT cycle counter, WFI/WFE, a cycle clock and a service hook where a chip
  model advances its peripherals. A future nRF52833, EFR32 or CC2650 reuses it.
- `emulator/src/nrf52/` (`nrf52emu::Nrf52840`) is the chip: peripherals at
  `0x40000000 + 0x1000 * id` (the id is also the interrupt number), the two
  GPIO ports, FICR/UICR.
- `emulator/src/sim/nrf52840_mcu.cpp` adapts it to the system layer (pads on
  nets, UARTs as endpoints, memory for RTT).

## The Cortex-M core and the Unicorn fork

Unicorn's ARM backend executes Cortex-M code but ships without the machinery
around it: its NVIC was commented out, and exception entry and return were
stubbed with `return; // FIXME`. The fork restores them
(`qemu/target/arm/nvic.c`, `m_helper.c`):

- `nvic.c` is a self-contained NVIC and System Control Space for the
  single-security-state ARMv7-M case: priorities with grouping, BASEPRI, PRIMASK,
  FAULTMASK, pending/active/enable state, fault escalation to HardFault, level
  and edge interrupts, and the register file firmware sees at `0xE000E000`
  (ICSR, VTOR, AIRCR, SHPR, SHCSR, CFSR/HFSR, CPACR, FPCCR, ISER/ICER/ISPR/ICPR/
  IABR/IPR, STIR). SysTick is not in the engine: the host owns time.
- Exception entry and return, tail-chaining and the FPU extended frame work as in
  QEMU. Lazy FP stacking is not modelled; the FP registers are always stacked
  eagerly when `CONTROL.FPCA` is set, which firmware cannot tell apart.
- `uc_ctl_set_cpu_model` is honoured for `UC_MODE_MCLASS` (the fork forced
  Cortex-M33 before), and SVC, faults and exception return are taken by the
  guest through `uc->guest_exception` instead of being reported to `UC_HOOK_INTR`.
- The host reaches the NVIC through `uc_arm_nvic()` (`include/unicorn/arm.h`):
  `UC_ARM_NVIC_SET_IRQ` drives an interrupt line, the `SCS_READ`/`SCS_WRITE` ops
  back the host-mapped SCS window.

Facts that matter when changing `core.cpp`:

- Every instruction goes through a code hook that counts cycles and checks the
  deadline. WFI/WFE/SEV/YIELD are decoded there and never reach the engine: the
  core stops, skips the instruction and sleeps (or sets the event register); a
  sleeping core jumps the clock to the next service deadline. WFE wakes on an
  event or on a pending enabled interrupt, WFI on a pending enabled interrupt.
- An interrupt line raised from an MMIO write is taken at the next translation
  block boundary, not on the next instruction.
- Each instruction costs `cycles_per_instruction` (1, inferred). A tight loop
  runs at about 175 million instructions per second on an Apple Silicon laptop,
  so a busy 64 MHz firmware runs roughly 2.5 times faster than real time;
  mostly-sleeping firmware (the usual case) is far faster.
- Flash is mapped read-only. A CPU store to it reaches the write-protect handler,
  which is how NVMC implements the "write can only clear bits" rule: the store
  is let through and the result is fixed up before the next instruction.
- `SYSRESETREQ`, a watchdog timeout and `SYSTEMOFF` leave `Core::run` with
  `StopReason::Reset`; the chip rebuilds the engine, keeps RAM and flash, and
  restarts. `POWER.RESETREAS` records the cause.

## Peripherals

Registers follow the nRF52840 Product Specification. Each source file says what
is documented and what is inferred.

| Peripheral | Id | Status |
| --- | --- | --- |
| CLOCK, POWER | 0 | HFCLK/LFCLK start events (short fixed delays), calibration, RESETREAS, GPREGRET, DCDC bits; no brown-out or USB events |
| UARTE0, UARTE1 | 2, 40 | EasyDMA TX/RX, ten bit times per byte, RX FIFO of four; the bit stream is not put on the pad (it idles high) |
| TWIM0, TWIM1 | 3, 4 | I2C master with EasyDMA and SHORTS; drives SCL/SDA bit by bit so I2C parts on the nets answer; no clock stretching |
| GPIO P0, P1 | - | OUT/DIR/IN, PIN_CNF (pull, drive modes incl. open-drain, SENSE), LATCH, DETECT |
| GPIOTE | 6 | 8 channels: edge events, output tasks, PORT event |
| SAADC | 7 | 8 channels, VDD and AIN inputs from nets, resolution, gain, differential mode, EasyDMA result, calibration; oversampling only scales time |
| TIMER0..4 | 8, 9, 10, 26, 27 | 16 MHz base, prescaler, bit width, compare/capture, SHORTS, counter mode |
| RTC0..2 | 11, 17, 36 | 24-bit counter, prescaler, compare/overflow events, TRIGOVRFLW |
| RADIO | 1 | IEEE 802.15.4 mode on the shared medium: ramp-up/disable, TX with the appended FCS, RX into RAM with FCS and ED byte, CCA, ED, SHORTS, events and interrupts; other modes (BLE) run the state machine only |
| TEMP | 12 | constant, configurable (`set_quarter_degrees`) |
| RNG | 13 | seeded PRNG (`set_device_id`), 30 us per byte |
| ECB | 14 | AES-128 block encryption of a RAM block |
| WDT | 16 | timeout event, reset two LF ticks later, reload registers |
| EGU0..5 | 20-25 | software events and interrupts |
| NVMC | 30 | flash and UICR programming/erase, instant |
| PPI | 31 | 20 programmable plus 12 fixed channels, groups, forks |
| FICR, UICR | - | read-only identity (derived from `set_device_id`), UICR programmable through NVMC |

Everything else (SPIM/SPIS, PWM, I2S, PDM, QDEC, COMP, CCM/AAR, USBD, QSPI,
NFCT, CryptoCell) is a register-only stand-in: values read back what was
written and no events ever fire. Firmware that waits for one of them stops at
the wait, which `--trace-mmio` makes visible.

## Board: Pro Micro

`examples/devices/nrf52840_promicro.yaml` is a nice!nano v2 style board with a
status LED (P0.15) and a button (P0.11). The sample Embassy Zigbee sensor image
(zigbee-rs `nrf52840-sensor`) was built for the nRF52840-DK, so its LED is P0.13:
the example world passes `led_pin: P0.13`. On a real nice!nano, P0.13 gates the
3.3 V regulator; the model does not wire it.

`examples/nrf52840_promicro.yaml` boots the image alone: UICR programming and
reset, clocks, SAADC VDD read, RNG and ECB use, RTC alarms, then active scans
that find nothing. `examples/nrf52840_zigbee.yaml` puts it on one medium with
the TLSR8258 sampleGW coordinator: the sensor finds the beacon on channel 15,
associates, receives the NWK key and completes the unique trust-center link key
exchange (Node Descriptor, Request Key, Transport-Key, Verify Key, Confirm Key
SUCCESS) with the Telink stack, about 21.4 s in (its first scan ends before the
coordinator has formed the network, so it joins on the second attempt). Two
different chips and cores on one timeline. The defmt log is on `board.mcu.rtt`.

The image needs the zigbee-rs fixes that start the End Device Timeout
negotiation after the exchange and take the exchange's frames with volatile
replay floors; earlier builds panic with "security persistence failure" on the
first secured frame, because the durable stores refuse replay counters until the
network is commissioned.

## The radio

`Radio` bridges frames to `mcuemu::VirtualAir` like the TLSR8258 does: PACKETPTR
holds the length (PHR, counting the two FCS bytes) and the MAC frame; on
reception the model writes the FCS (the real CRC-16) and then one energy-detect
byte (`clamp(RSSI + 92, 0, 63)`, the value the Nordic stacks multiply by 4 for the
LQI). The medium carries MAC frames without the FCS, so a frame is 64 us shorter
on air than on a real radio.

Timing that matters for MAC acknowledgements: the receiver polls the medium every
16 us while listening, a ramp-up takes 130 us (40 us with `MODECNF0.RU`), and a
frame can still be received if listening starts before its start-of-frame
delimiter (128 us after its first bit). The Embassy MAC re-arms the receiver
about 150 us after a transmission ends and the peer's ACK starts 192 us after
the frame, so this margin is what lets the ACKs of the TLSR8258 coordinator
(sent by its firmware) reach the sensor. A network whose coordinator does not
acknowledge needs its own auto-ACK; the model has none.

## Tests

- `nrf52emu-tests`: the core (SVC, nested IRQs, FPU context, WFE sleep, SysTick,
  BASEPRI, level interrupts, reset, breakpoint, flash store), every peripheral
  above except TWIM, and the RADIO (frame exchange between two chips, CCA, ramps). The test programs are assembly in
  `tests/nrf52/programs/*.s`; `programs/build.py` regenerates the committed
  `tests/nrf52/programs.hpp` (needs `arm-none-eabi-as`).
- `simcore-tests` (`tests/sim/test_nrf52.cpp`): pads on nets, TWIM against an
  `i2c_regs` device (write, repeated-start read, address NACK), UART endpoints.
- `firmware_nrf52840_boot` runs the sample image when
  `firmware/nrf52840-sensor.bin` is present and follows its start-up in the
  register trace; `firmware_nrf52840_zigbee_join` (also needs
  `samplegw_tb03f.bin`) runs the two-chip network and checks the join.

## Status

Done: CPU with NVIC/SysTick/FPU/WFE, flash and RAM, the peripherals above, the
board example, the sample Zigbee sensor image boots to its idle loop.

Not done:

1. BLE on the RADIO (the medium has a BLE path; the register model has none).
2. SPIM/SPIS, PWM, CCM/AAR, USBD, QSPI and the rest of the stand-ins.
3. Cycle-accurate timing: every instruction is one cycle, there is no flash wait
   state or cache model.
4. Other family members (nRF52833, nRF52832) differ in memory sizes and the
   peripheral set; `Nrf52840` is the only chip class so far.
