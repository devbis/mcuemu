# BL702 (XT-ZB1): status and plan

The Bouffalo BL702 is a RISC-V SoC (the zigbee-rs firmware is built for `riscv32imc`, with the
CPU clock at 32 MHz from the 32 MHz XTAL) with an IEEE 802.15.4 radio. The DOIT/XT-ZB1 module is the board the zigbee-rs
`bl702-sensor` example targets. The model is `model: bl702` in the system config and
`bl702emu` (`emulator/include/bl702emu/bl702.hpp`) in the code. The zigbee-rs sources
it runs (`zigbee-mac/src/bl702/`, `bl702-hal/`, `boards/bl702-xt-zb1/`,
`products/bl702-xt-zb1/`, `examples/bl702-sensor/`) are not in this repository.

Not modelled: USB (not needed for the sensor; the board's SPI header shares GPIO7/GPIO8 with
it), GPIO pads (`connect_pin` refuses the model's pads), ADC, I2C, SPI, PWM, UART receive and the low-power
states (PDS/HBN). The SPI flash command interface of bank 1 is modelled (identification, status,
reads, page program, the 4 KiB/32 KiB/64 KiB and chip erases). The Bouffalo binary radio library (`lmac154`)
is not needed: zigbee-rs drives the radio registers directly.

## Memory map

| region | address | size | model |
|---|---|---|---|
| boot ROM | 0x21000000 | 128 KiB | host stand-ins, see below |
| XIP flash | 0x23000000 | 1 MiB | window onto the flash (see the boot header) |
| SRAM | 0x42010000 | 128 KiB | host RAM, zeroed at reset |
| ITCM | 0x22014000 | 16 KiB | host RAM (Zephyr copies its code here) |
| L1 cache controller | 0x40009000 | | `L1c`: the operation-done bit reads 1 |
| peripherals | 0x40000000 | 64 KiB | blocks below; other registers read back what was written |
| CLINT (machine timer) | 0x02000000 | 64 KiB | `Clint`: mtime at 1 MHz, mtimecmp, msip |
| CLIC, hart 0 | 0x02800000 | 4 KiB | `Clic`: pending, enable and level per interrupt |
| M154 (802.15.4 MAC) | 0x4c000000 | 4 KiB | `Ieee802154` |

## Boot

`Bl702::reset()` plays the boot ROM. The flash image starts with the 176-byte boot
header (`BFNP` magic; the layout is `bflb-mcu-tool`'s `bootheader_cfg_keys.py`):

- word 116 bit 8 (`no_segment`): when clear, a segment list follows the header; each
  segment is a 16-byte header (load address, length, data CRC, header CRC) and its data.
- a segment whose load address is in SRAM is copied there.
- a segment whose load address is in the XIP window maps its data (the flash bytes
  right after its header) at that address. This is how `bflb-mcu-tool` lays out a
  linked XIP image: its `img_addr` is both the segment's load address and `img_start`.
- word 124 is the entry point and the core starts there.

The header's hash and CRCs are not checked. A flash without `BFNP` at offset 0 fails
to load.

**Inferred, not checked against a real image:** that the XIP window follows the XIP
segment as above, and that `bootentry` is an absolute address. Both come from reading
`bflb-mcu-tool` 1.10.0, not from a board. Checking them needs a real image (see below).

## Boot ROM stand-ins

The HAL calls the ROM through the table at 0x21018800 (`bl702-hal/src/flash.rs`). Each
entry points at its own `ebreak` stub; the core stops there and the chip runs host code:

- 157 `load flash config`: copies the 84-byte flash configuration of the boot header.
- 78 `erase`, 79 `write`, 80 `read` (the XIP routines): operate on the physical flash
  at a flash offset. A write only clears bits (NOR flash); an erase sets a 4 KiB sector
  to 0xff. Afterwards the XIP window follows the flash, and translated code is dropped.
- 121 cache flush and 144..146 the flash controller's AES switch: no-ops (the cache and
  the controller's AES are not modelled).

Any other entry returns 0 without running anything.

## Peripherals

| block | registers | what it does |
|---|---|---|
| GLB, HBN, ADC, I2C, SPI, PWM, SEC_ENG (except AES), L1C | | read back what was written; no behaviour |
| UART0 `0x4000a000` | FIFO_WDATA 0x88, FIFO_CONFIG_1 0x84 | transmit: each byte goes to the system at once; the FIFO reports room |
| TIMER0 `0x4000a500` | COUNTER 0x2c, ENABLE 0x84, DIVIDER 0xbc | a counter at 1 MHz (one tick every divider+1 cycles); no compare interrupts |
| eFuse `0x40007000` | WIFI_MAC_LOW 0x14, WIFI_MAC_HIGH 0x18 | the chip ID, the eight MAC bytes in order; read-only |
| SEC_ENG AES `0x40004100` | CTRL 0x00, MSA 0x04, MDA 0x08, KEY 0x20..0x2c | ECB, one run of CTRL's MSG_LEN blocks; instant |
| RF/PHY `0x40001000` | PHY_CCA_ENABLE 0x82c, PHY_CCA_CTRL 0x834, PHY_RSSI 0x860 | CCA result on the air; RSSI of the last frame |
| M154 `0x4c000000` | see below | transmit, receive, CCA inputs, interrupt status |

**Documented by the zigbee-rs driver (which reads the register sequence the hardware
needs):** the register offsets and the bits the driver tests (`radio_phy.rs`, `rf.rs`,
`registers.rs`), the chip ID byte order (`efuse.rs`), the AES key byte order (the driver
writes each key word little-endian, and the model reads it that way; with a
FIPS-197 vector the result is the standard one, which the driver's own startup test
checks on silicon).

**Inferred:**

- Timer and MAC clock: 1 MHz from the 32 MHz clock (the SDK divider 31).
- M154 transmit starts at once. The frame goes on the shared air without the FCS (the
  medium's convention; `airtime_ns` counts it), the hardware appends it and PHR counts it.
- M154 receive polls the air every 16 us. A frame that ends during the model's own
  transmit is not heard (half duplex).
- Raw RSSI is 5 - dBm, as the driver converts it (`rf` CCA and `rssi_to_ed`).
- CCA is busy when a frame on the channel is at or above -(threshold field), the field
  being bits 16..22 of PHY_CCA_CTRL (76 in the driver, so -76 dBm). Energy detect
  reports the strongest frame, or -100 dBm (the noise floor) when none is on the air.
- The AES MSG_LEN field counts 16-byte blocks; the driver uses 1.
- `M154_STATE` reads 1 in the low 11 bits when the MAC is idle, which is what the
  driver's `is_idle` needs; the upper bits read back what was written.
- The reset of a transmit (M154_RESET = 24) forgets the frame in the transmitter but not
  the copy already on the air.

### RF calibration

The driver calibrates the RF block at boot (ACAL, KCAL, ROSCAL, RCCAL). Each step is
gated by a flag at 0x4000100c, and the flags read 0 here, so the driver skips them all.
The analog state the calibration sets is therefore not modelled, and neither is any
calibration result. On silicon the flags are nonzero after a cold boot (the code
expects them so); that is inferred from the driver, not measured.

## The sim adapter

`model: bl702` in a system YAML (`sim/bl702_mcu.cpp`): `firmware:` is the flash image
(placed at offset 0 by default); `radio:` takes `protocols: [zigbee]`; `variant`,
`clock_hz`, `supply_mv` and `flash_timing` are rejected. The UART0 bytes come out of the
MCU's `uart0` endpoint. The EUI-64 the eFuse reports is derived from the MCU's instance
name (FNV-1a), so two BL702 nodes never share an address.

`examples/bl702_zigbee.yaml` puts an XT-ZB1 sensor next to the TLSR8258 coordinator. It
expects the sensor image at `firmware/bl702-xt-zb1.bin` (local, not committed).

## Tests

`bl702emu-tests` (`tests/bl702/`): the boot header (segments, XIP segment, rejection of a
header-less flash), UART and TIMER0, the eFuse and AES (FIPS-197 C.1), the M154 transmit
and receive through the shared air, CCA, and a guest program that calls the ROM's flash
write through the table. `simcore-tests` (`tests/sim/test_bl702.cpp`): the adapter in a
system, UART output through the endpoint, a transmit on the world's radio, and the config
rules.

The guest programs are hand-encoded or assembled with `llvm-mc` (no linker is needed when
the code has no relocations; `llvm-objcopy -O binary -j .text` takes the bytes).

- The boot-image assumptions above, the AES byte order on silicon, and the calibration
  flags.
- Timing: the transmit turnaround, the poll period and the CCA threshold are estimates.

## Interrupts (CLIC) and the Zephyr image

The Zephyr build (board `dt_xt_zb1_devkit`, SoC `bl702c10q2h`) uses the SiFive-draft CLIC in
non-vectored mode: `mtvec` mode 3 with the common entry at its base, and the handler claims the
interrupt with `mnxti` (CSR 0x345). The model follows that:

- The fork (`engine/unicorn`, `qemu/target/riscv`): `mtvec` mode 3 is accepted; `mtvt` (0x307),
  `mintthresh` (0x347), `mintstatus` (0xfb1, the level `mil` in bits 31:24) and `mnxti` are
  CSRs of the hart. A trap that takes an interrupt sets `mil` to the interrupt's level and saves
  the previous level in `mcause[23:16]`; `mret` restores it. The host picks the interrupt through
  `uc_riscv_clic` (the highest pending level above `mil` and `mintthresh`); a `mnxti` read claims
  it and returns `mtvt + 4 * number`, which Zephyr turns back into the number.
- Inferred, from the Zephyr image: the BFLB SoC gives its machine timer level 0, and it is taken
  while no interrupt is active (`mil` 0). The rule is: taken when `mil` is 0 or the level is
  above `mil`, and the level is at least `mintthresh`.
- `Clint`: `mtime` counts `cycles / 32` (the 1 MHz timebase); `mtimecmp` raises CLIC line 7.
  `msip` raises line 3. The 802.15.4 block raises line 64 while an enabled status bit is set.
  Level lines are not cleared by a claim; the handler clears its source.
- Shared with the fork: the choice callback runs inside the translated code and does not touch
  the engine. The hart's `wfi` wakes when `Bl702::sync_interrupts` reports a pending interrupt.
- The hart model is the SiFive U34 (`riscv::Core::Config::fpu`): the zigbee-rs and Zephyr
  images use single-precision instructions, and the E31 model has no FPU.

`tests/bl702/` has a program that uses the timer through CLIC: mtvec mode 3, the handler claims
with `mnxti`, counts the entry, and returns with `mret`.

## The Zephyr router image (`zephyr.bin`, not zigbee-rs)

A raw Zephyr binary has no boot header. `scripts/bl702-wrap-image.py` writes one the way
`bflb-mcu-tool` does for an XIP image: the `BFNP` header, the `FCFG` flash configuration from a
flash `.conf` (for the XT-ZB1, `utils/flash/bl702/KH25V80_c22014.conf` of the tool), its CRC-32,
one segment header and the binary. Arguments: the binary, the output, the entry, the load address
(`zephyr.elf`'s entry and the lowest load address), the `.conf` and the tool's
`bootheader_cfg_keys.py`. The Zephyr code copies its own ITCM and RAM sections from the XIP image.

Status with that image (`router-dbg`, Zephyr 4.4, the zigbee stack):

- It boots: the reset path, the ITCM copy, the CLIC, the machine timer and the 802.15.4 interrupts
  work, and the console prints through UART0.
- The flash driver initialises (the XIP offset register at SF_CTRL 0x434, the SPI command
  interface at 0x4000B008 with the data buffer at 0x4000B700); the NVS store works.
- The router scans channels, finds the coordinator's beacon, sends its association request, gets the
  coordinator's ACK and the association response, and joins the network (`app_bdb: joined network`,
  about 7.9 s of simulated time, `zigbee_shell` with the TLSR8258 `telink-gw` coordinator).
- Two model gaps stopped the join, both fixed:
  - The TRNG (SEC_ENG, 0x40004200) was unmapped. The Zephyr driver read zeros, so `sys_rand_get` gave
    the router an all-zero EUI-64 (02:00:00:00:00:00:00:00), and the stack addressed its frames to it.
    The model now fills the TRNG output on a trigger (fixed-seed xorshift; the driver's BUSY bit stays 0).
  - The M154 did not acknowledge unicast frames addressed to it. The driver advertises
    `IEEE802154_HW_RX_TX_ACK`, so the hardware sends the ACK. The coordinator did not get it and gave up on
    the association response, so no Transport-Key came. The model now acknowledges a frame that asks for
    it and is addressed to the EUI the library wrote (words 0xd0 and 0xd4, found by a dump: inferred), one
    turnaround time (192 us) after the frame ends.
- A real board has a working TRNG and hardware ACKs, so these two gaps do not explain a failed join on
  hardware. The cause there is not established: it needs a trace from the board (the association
  response and the poll it sends after the response).
- Inferred from the library's code and used by the model: the six M154 timer channels (target at
  0x64 + 4n, counter at 0x40 in 16 us symbols, enable bit n of 0x20, status bit n of 0x30), RX completion
  as RX_CRC (bit 19) plus RX_DONE, and the receiver state as bit 12 of RX_CONTROL as written.
